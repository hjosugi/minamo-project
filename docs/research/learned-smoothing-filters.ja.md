# 調査: One Euro 後継としての学習型平滑化フィルタ

ステータス: issue #270 の調査パス。同 issue が求めるベンチマークを構築し、ベースラインを実測した。関連:
[../benchmarks/filter-response.md](../benchmarks/filter-response.md),
[../benchmarks/hand-stability-report.md](../benchmarks/hand-stability-report.md)。

## Goal

FLK、HPSTM/Real-Time ESFP、SmoothNet のいずれかが平滑化スタックのどこかで One Euro を置き換えるべきかを判断する。そして #270 がまず求めているとおり、そうした主張を検証可能にするベンチマークを定義し計測する。

## Acceptance criteria

- [x] Goal が明確である。
- [x] Acceptance criteria が明確である。
- [x] 既存設計と矛盾しない: One Euro がデフォルトのまま維持され、候補はスタック全体ではなく特定チャンネルに限定される。
- [x] **ベンチマークの定義**: `scripts/bench-filter-response.mjs` (`pnpm bench:filters`) のジッタ・ラグ・オーバーシュート・持続運動追従。参照フィルタに対して自己チェックする。
- [x] **ベースラインの採点**: 3プリセットと5グループ既定値のすべてを [../benchmarks/filter-response.md](../benchmarks/filter-response.md) に記録。
- [x] 候補ごとの決定の文書化、および候補が超えるべき基準。
- [ ] FLK を pose チャンネルで移植・実行し同一ラグで比較する。**未実施** — 上流が Python/PyTorch であるためモデルの JS または ONNX への移植が必要で、下記の「どのチャンネルに適用しうるか」の知見にゲートされる実装作業である。

## Findings

### 候補が対象とするのは、本プロジェクトが主に平滑化していない対象である

これが issue の枠組みを変える知見である。FLK、HPSTM、SmoothNet はいずれも **3D キーポイント軌跡** のフィルタである。トラッカーが実際に One Euro をかけている対象は:

| フィルタ | チャンネル数 | 種類 |
|---|---|---|
| `weightFilter` | 52 | [0,1] の ARKit ブレンドシェイプウェイト |
| `quatFilter` | 4 | 頭部回転クォータニオン (正規化付き) |
| `posFilter` | 3 | 頭部位置 (メートル) |
| `poseFilter` | 21 | 上半身7点 × 3 — **唯一のキーポイント** |
| `handCurlFilter` | 10 | 指ごとの curl (派生スカラー) |
| `handSpreadFilter` | 10 | 指ごとの spread (派生スカラー) |

つまり平滑化対象の約100スカラーのうち **21 が 3D キーポイント** である。FLK の空間コアは「人体の生体力学的制約 … キーポイント間の空間的整合性」であり、HPSTM のデコーダは「一定の骨長と解剖学的妥当性」を強制する。いずれもブレンドシェイプウェイト、クォータニオン成分、指ごとの curl スカラーに対して制約すべきものを持たない。`jawOpen` と `browInnerUp` の間に骨はない。

#270 の「平滑化スタック全体が One Euro フィルタである」という前提は正しい。しかし、ゆえに学習型キーポイントフィルタがスタックを置き換えられるという推論は成り立たない: せいぜい pose ブロックに対応するだけである。

### そして pose ブロックですら適合度は低い

pose ブロックは7点 — 鼻、両肩、両肘、両手首 (`shared/blendshapes.js` の `POSE_POINTS`) である。FLK の生体力学的制約と HPSTM の順運動学デコーダはどちらもより完全な骨格を前提とする。腰・脊椎・脚がなければ活用できる運動学的構造はほとんど残らず、その制約機構こそがこれらのフィルタを十分に調整されたローパスから区別している主要部分である。

FLK の報告された改善も、本プロジェクトが重視する量とは別物である: 「非ガウスノイズで最大 140 mm、欠損情報で 53 mm の精度改善」は **劣化した入力に対する誤差削減** — 外れ値とフレーム落ち — であって静止時のジッタではない。それらは実在の問題だが、トラッカーはフレーム落ちを別レイヤ (`TrackingLossSmoother`、`HandTargetStabilizer` のオクルージョン保持) で既に扱っており、明言された最優先事項はジッタである。真値モーキャプに対する MPJPE で評価されたフィルタは、60 fps で目に見える揺れを減らすことを示したわけではない。

### 3候補のうち2つは非因果であり、これは失格要件である

- **HPSTM / Real-Time ESFP** は「自己注意により長距離時間文脈と微分可能な順運動学デコーダを組み合わせる seq2seq Transformer」である。長距離時間文脈とは未来フレームを意味する。#270 はこれを「より重い。デスクトップ層の選択肢として評価」と分類しているが、問題は重さではない — 非因果な平滑化器はフレーム *n+k* が存在する前にフレーム *n* を出力できない。どの層であっても同じである。出典論文の対象は 4-DoF デスクトップロボットアームを駆動するパイプラインであり、ライブアバターではない。
- **SmoothNet** はウィンドウベースであり、#270 が既に「レイテンシを増やす — ベースラインのみ」と分類している。同意する。構造的理由も同じである。
- **FLK** は唯一の因果的候補である: 学習済み運動モデルを持つ適応カルマンフィルタで、ゼロ/低レイテンシかつリアルタイムと記述されている。

したがってライブ候補の母集団は3ではなく1である。

### ベンチマークが露わにした、より安価な改善余地

ベースラインを計測した結果、3つのプリセットは `(minCutoff, beta)` 空間を張っていないことが判明した。`headRotation` の既定値 (1.2, 0.8) は `balanced` プリセット (1.6, 0.4) をジッタ (0.085 対 0.106) と ステップラグ (100 対 133 ms) の両方で上回り、その代償は持続運動の追従のみである (RMSE 0.0581 対 0.0543)。`beta` — 固定ローパスに対する One Euro の存在意義そのものである適応微分ゲイン — はプリセットの階段が示唆する以上に働いている。

`pnpm bench:filters` によるこの空間のスイープは数分で済み、新規依存も不要である。60 fps ループにニューラルネットワークを載せる提案の前に、これを尽くすべきである。もしスイープが利用可能な改善の大部分を回収するなら、学習型フィルタは #270 が想定したよりずっと強いベースラインを超えなければならなくなる。

## Decision

**全チャンネルで One Euro をデフォルトのまま維持する。** ここに移行を正当化するものはなく、将来の主張を検証するベンチマークは整備された。

**HPSTM / Real-Time ESFP: ライブ経路では不採用。** 単に重いのではなく構造上非因果である。未来フレームが無償であるオフライン経路 — 収録後の平滑化 — でのみ再検討する。それはライブ平滑化とは別機能であり、現時点で要望されていない。

**SmoothNet: 不採用、ベースラインのみ。** #270 の提案どおり。ウィンドウベースである。

**FLK: 唯一のライブ候補として保持するが、pose ブロックに限定する。** ブレンドシェイプ・クォータニオン・curl チャンネルには移植しないこと: そこでは生体力学コアが無意味になり、残るのは1次元信号上で十分調整された One Euro と競合する学習型カルマンフィルタであって、論文の結果が示唆するよりはるかに弱い提案となる。移植に着手する前に下記のスイープを実施し、FLK を計測する際は [../benchmarks/filter-response.md](../benchmarks/filter-response.md) の4基準、とくにオーバーシュート (学習済み運動モデルを持つカルマンフィルタは生じうるが One Euro は生じない) に照らして判定すること。

**まずプリセットスイープを行う。** ここで得られる期待利得とリスクの比が最も高く、依存関係も不要で、いかなる学習型フィルタも超えるべきベースラインを鋭くする。
