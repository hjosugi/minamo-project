# 調査: SMIRK 系の表情キャプチャと MobileGaze

ステータス: issue #273 の調査パス。全候補がライセンスと出力空間で決着し、いずれもハードウェアを要しない。関連: granular backlog 039–053 (face), KGM-016 (真の視線), `DD-006-kgm2.md`,
[face-quality-benchmarks.md](../benchmarks/face-quality-benchmarks.md) (#106, #107),
[occlusion-robust-hands.md](occlusion-robust-hands.md) (#271),
[onnx-wholebody-pose.md](onnx-wholebody-pose.md) (#269)。

## Goal

SMIRK 系の FLAME 表情キャプチャをオプションの品質モードとして導入する価値があるか、および MobileGaze が既存のアイリスランドマーク視線を置き換えるべきかを判断する。

- [ ] ONNX エクスポートと WebGPU/WASM での fps。**未実施** — #222/#269 と同じ `onnxruntime-web` の依存レビューにブロックされており、出荷できない候補については無意味である。

## Findings

### この issue の FLAME に関する前提は古く、その訂正には意味がある

#273 は *「FLAME license is non-commercial — license review is the gate」* と述べている。かつては真だったが、一般論としてはもう真ではない。**FLAME 2023 Open は CC BY 4.0 で公開されており**、商用利用を含む任意の目的での共有と改変を明示的に許諾している。それ以前のモデル (2017, 2019, 2020, Blender アドオン) は非商用のままで、商用・軍事・監視利用を禁じ、それらの用途向けの手法の学習も禁じ、再配布も禁じている。

したがって「FLAME ベースであること」はもはや一律の失格事由ではない。問われるのは *その手法がどの FLAME に対して作られたか* である。

SMIRK についての答えは悪い方である。`quick_install.sh` は登録プロンプトの背後にある MPI のエンドポイントから **FLAME2020** をダウンロードし、さらに **EMOCA の ResNet50** と **MICA** も同じく MPI から取得する。SMIRK 自身の MIT ライセンスはコードを覆うが、これら3つの資産には及ばず、公開されている SMIRK のチェックポイントはそれらを用いて生成されている。

**つまりゲートは「FLAME」ではなく、SMIRK が同梱する形での FLAME2020 + EMOCA + MICA である。** この区別を保つことが有用な部分である — 将来の FLAME-2023 ベースの手法は自動的に排除されない。ライセンスの扉が少しでも開いているのは、直近3回の調査パスで初めてである。

これは #273 の「別途インストールするオプションモード」という枠組みも否定する。資産は再配布できないため、利用者自身が MPI に登録して非商用ライセンスに同意する必要があり、そのうえで非商用条項はその後の利用も規律し続ける。そのモードの背後に出荷可能な既定は存在しない。

### SMIRK の出力は本プロジェクトの出力ではなく、そのコストはライセンスより大きい

エンコーダは1つではなく **MobileNetV3 バックボーン3本**である: pose に `tf_mobilenetv3_small_minimal_100`、shape に `tf_mobilenetv3_large_minimal_100`、expression にも同じ large バックボーン。出力は pose/camera 6 + shape 300 + expression 50 + eyelid 2 + jaw 3。

KGM1 が運ぶのは **52 の ARKit ブレンドシェイプ**である (`shared/blendshapes.js` の `NUM_CHANNELS = ARKIT_52.length`)。ワイヤ上では u8 に量子化され (`FACE_BYTES = 66`)、MediaPipe はその52をそのまま出力している。

FLAME の 50 の expression パラメータはメッシュ基底上の PCA 係数である。ARKit セットの部分集合ではなく、**別の基底**である。したがって「FLAME→ARKit リターゲティング」はルックアップテーブルではなく、トポロジごとにフィッティングされる写像である。これは #269 の RTMW (68 ランドマークは 52 ブレンドシェイプになれない) や #271 の MANO メッシュと同型の問題であり、しかもより難しい版である — ランドマークは少なくとも顔と同じ幾何空間に存在する。

反対側の帳簿に記録しておくべき点が2つある。誤解しやすいためである:

- **SMIRK は本質的に重くはない。** その貢献である analysis by neural synthesis は*学習時*の構成である。推論時にはエンコーダだけである。
- **shape は表情ではなく個人性である。** 300 の shape パラメータは利用者ごとに定数であり、大きい ShapeEncoder は毎フレームの経路ではなくキャリブレーション工程に属する。リアルタイム予算は小さい pose エンコーダ + large の expression エンコーダ1本になる。これは測定値ではなく見積りであり、測定は #222 と同じ `onnxruntime-web` レビューにブロックされている。

### 後継研究はライセンス面でより良くなく、より悪い

- **TEASER** (ICLR 2025, `Pixel-Talk/TEASER`) — リポジトリは**ライセンスを一切宣言していない**。明示的な許諾がない場合の既定は全権利留保であり、これは #271 の ReJSHand の所見そのものであって、許容的ライセンスより緩いのではなく厳しい立場である。最終 push は 2025年4月。
- **SuperFace** (arXiv, 2026年5月) — コードは見つからず、arXiv の掲載は **CC BY-NC-ND**。ただし前提は3件中もっとも興味深い: **ARKit** 係数を直接予測し、ソフトウェア生成の疑似ラベルを超えて、レンダリングされた表情に対する人間の選好フィードバックで洗練する。もし許容的な条件でコードが公開されれば、本プロジェクトの出力空間を狙っておりリターゲティング問題を丸ごと回避するため、SMIRK より厳密に適合する。監視対象。計画に組み込む対象ではない。

### MobileGaze のコードは MIT であり、重みは出荷できない

リポジトリは MIT、全バックボーンの ONNX を同梱し、MobileOne-S0 は **4.8 MB** — まさに本プロジェクトが許容できるサイズ帯である。

そして **全モデルが Gaze360 のみで学習されている**。Gaze360 のライセンスは非商用の研究利用限定であり、決定的な条項は画像を超えて及ぶ: 当該素材は「いかなる形でも商用アプリケーションに使用または包含してはならない (オリジナルファイル、暗号化ファイル、抽出特徴を含むファイル、**データセットで学習されたモデル**、その他の派生物等)」。

つまりこれは #271 の MANO パターン、#278 の CC BY-NC パターンに続く3回連続の同型である: **非商用の成果物の上に載った許容的コード。** コードは再利用できる。重みはできず、再学習には許容的ライセンスの視線データセットが必要で、それは #271 の AnyHand の注記がぶつかったのと同じ欠落である。

### ライセンスを措いても、ここで優れているという公表値は存在しない

| モデル | サイズ | Gaze360 MAE |
|---|---|---|
| MobileOne-S0 | 4.8 MB | 12.58° |
| MobileNet V2 | 9.59 MB | 13.07° |
| ResNet-18 | 43 MB | 12.84° |
| ResNet-34 | 81.6 MB | **11.33°** |
| ResNet-50 | 91.3 MB | 11.34° |

比較対象として: `tests/run-tests.mjs:1529` はキャリブレーション済みアイリス視線が目標の **5°** 以内に入ることを表明しており、`gazeAngularErrorDegrees(actual, target, maxDegrees = 20)` は正規化された ±1 の視線全域をおよそ ±20° に対応させている。12.58° の平均誤差はこの正規化単位で 0.63 — 利用可能な半域の大半にあたる。

**この比較は慎重に扱う必要があり、慎重版でもなお決定的である。** Gaze360 はカメラに背を向けた被験者を含む 360° の頭部姿勢にまたがる。正面のみの誤差ははるかに小さく、リポジトリは正面での数値を公表していない。したがって結論は「MobileGaze が劣る」ではない。**本プロジェクトの条件下で優れていることを示す公表値が存在しない**ということであり、入手可能な唯一の数値は、着席した VTuber が決して生成しない分布上で測られている。5° の数値も合成データ由来であり、両側とも実クリップ上では未測定である — それ自体が所見である。

置き換えが見た目ほどの勝ちにならない理由がもう1つある: MobileGaze は**カメラ**座標系の yaw/pitch を出力するが、本プロジェクトの視線は画面相対の正規化 `(x, y)` であり、`buildGazeCalibrationProfile` が5点注視フローから center と scale を利用者ごとにフィッティングしている。モデルを差し替えてもこのアフィン補正は消えない。新モデルの精度が何であれ、アバターに届くのは同じキャリブレーションを通過した後の残りである。

### 視線は、ワイヤ形式が制約に*なっていない*唯一の信号である

これは #269 と #271 の逆であり、その2パスが逆の反射を作ったからこそ明記する価値がある。`docs/design/DD-006-kgm2.md` はブロックビット 2–5 を予約し、そのうち1つを明示的に命名している: **GAZE (KGM-016 真の視線ベクトル)**。KGM2 には既に真の3D視線ベクトルの枠がある。

現行実装はそれを使っていない。`shared/runtime.js` の `applyGazeToWeights` は8つの ARKit `eyeLook*` チャンネルをゼロ埋めし、アイリス推定値を `x` → `eyeLookOut/In`、`y` → `eyeLookUp/Down` として書き戻す。これらは u8 の重みとして送られ、各レンダラはそれを2つの数値に畳み戻す: `vrm_mapper.ts:43` は `leftEye.gaze.x` と `rightEye.gaze.x` を平均して yaw にし、Live2D は `ParamEyeBallX/Y`、Inochi2D は `eye_x/eye_y` を取る。**`gaze.z` は `src/core/face.ts` で計算され、どこからも消費されていない。**

つまり今日の視線の天井は、ブレンドシェイプチャンネルを経由させられた u8 量子化のスカラ2つである — が、それはプロトコル枠が既に予約された状態での実装上の天井であって、手や顔のように形式そのものが壁になっているのとは違う。視線品質に投資する価値があるなら、安い一手はモデル差し替えではなく KGM-016 の GAZE ブロックである。

### Baballonia の先例は非商用プロジェクトであり、転用できるのはモデルではなくデータ

#273 は Project Babble の Baballonia を、小さなカスタムモデルが OSS プロジェクトで保守可能である証拠として挙げている。確認した:

- **ライセンス**: 「Babble Software Distribution License 1.0」 — Apache-2.0 の本文に **Section 10「Additional Terms: Non-Commercial Copyleft Provisions」** を加えたもの。販売不可、当該成果物を中心とした有料サービス不可、収益化されるハードウェアへの統合不可、派生物は同一ライセンスでの公開が必須。挙げられた先例自体が非商用かつコピーレフトであり、そこから何かをベンダリングすることはできない。
- **モデルは転用できない。** 学習対象は「顔の下半分から4インチ、画角160度の近接・広角画像」 — ヘッドセット搭載カメラである。その幾何に合わせて調整された EfficientNetV2 の改造版は、本プロジェクトの唯一のケースである正面ウェブカメラの表情キャプチャについて何も語らない。

**転用できるのは、彼らがデータ問題をどう解いたかである。** 本番モデルは Synthetic Dataset v2 — 顔形状・肌テクスチャ・カメラ位置・照明を変えて3Dアセットからレンダリングしたもの — で学習され、髭や異常な角度といったエッジケースには実利用者からの提供データを取り込んでいる。

これが引用から得られる本当の教訓であり、直近3回の調査パスを止めてきたブロッカーへの回答でもある。欠けているのは常にアーキテクチャではなく、許容的ライセンスのデータセットである。この規模の OSS プロジェクトは、それを学術データセットのライセンス取得ではなくレンダリングによって解決した。

## Decision

1. **SMIRK は、別途インストールするオプション品質モードとしても不採用とする。** FLAME2020 + EMOCA + MICA は非商用かつ再配布不可であり、そのモードの背後に出荷可能な既定が存在しない。仮にライセンスが解決しても、50 の FLAME expression 係数は、本プロジェクトが実際に送信している 52 の ARKit チャンネルに届くまでにフィッティングされた基底変換を要する。
2. **TEASER は不採用** — ライセンス未宣言、すなわち全権利留保。**SuperFace は監視**する — ARKit 係数を直接狙っており出力空間として正しいが、コードがなく掲載は CC BY-NC-ND である。
3. **MobileGaze の重みは採用しない。** MIT のコードだが土台は Gaze360 であり、そのライセンスは「データセットで学習されたモデル」を名指ししている。許容的ライセンスの視線データセットが現れた場合、コードは出発点として有効なままだが、重みはそうではない。
4. **MediaPipe Face Landmarker のブレンドシェイプと既存のアイリス視線を維持する。** 本パスで監査したもののうち、本プロジェクトが出荷できる条件でこれを上回るものはない。
5. **顔と視線の品質に投資する価値があるなら、順序はこうである** — いずれも新モデルを要さない: (a) 5° が合成値である以上、まず現行の視線を実クリップで測る。(b) KGM-016 の予約済み GAZE ブロックを実装し、ベクトルを u8 の `eyeLook*` チャンネル経由で洗浄するのをやめ、`gaze.z` を捨てるのをやめる。(c) その後にはじめて、測定済みのベースラインに対してモデルを再評価する。
6. **FLAME 2023 の訂正を記録する。** 次の FLAME ベース候補は、ファミリ名ではなくどの FLAME バージョンに対して作られたかで判断すべきである。
7. **繰り返し現れるブロッカーはモデルではなくデータである。** 3パスにわたり4件の候補が、コードは許容的でありながら非商用の学習資産で落ちている。合成データ生成 — Babble の経路 — は、これまでに監査した中で許容的ライセンスの土台を生む唯一の道であり、次のモデルをレビューする前にそれ自体を評価する価値がある。
