# 調査: ONNX 音声→ARKit リップシンクモデル

ステータス: issue #268 の調査パス。[DD-003](../design/DD-003-audio-lipsync.md) が確保した「v2 small ML」枠の学習済みモデル候補を評価する。
関連: KGM-045, KGM-046, #222 (共通する ONNX Runtime Web 依存関係)。

## Goal

wav2arkit_cpu、LAM_Audio2Expression、NVIDIA Audio2Face-3D のいずれかが、出荷中のエネルギー/ヒューリスティックのリップシンクを置き換えるべきか、またどの条件下でかを判断する。DD-003 は既に枠を確保している — 「Small ML (v2): log-mel フレーム上の小さな CNN/GRU … ONNX Runtime Web (wasm EP) 経由 … (1) を先に出荷し、(2) は同じインターフェースの背後に」— したがって問題は設計が学習済みモデルを許容するかではなく、この3つのいずれかがその設計が約束するレイテンシ予算に実際に収まるかである。

このパスはドキュメントレベルである: ライセンス、成果物の形状、レイテンシの計算を上流の情報源から確定させ、結果を決める単一の計測項目を正確に述べる。

## Acceptance criteria

- [x] Goal が明確である。
- [x] Acceptance criteria が明確である。
- [x] 既存設計と矛盾しない: 採用されるモデルは DD-003 の既存の融合ルールの背後に置かれ、同じ ARKit の口チャンネルを駆動するため、プロトコルは変更されず、視覚の信頼度が高いときは形状の所有権は視覚側に残る。
- [x] 各候補のライセンスレビュー (再配布、商用利用)。
- [x] モデルごとの決定の文書化 — adopt / adapt / reject。
- [x] DD-003 の予算に対するレイテンシ **分析**。issue の計画が引いていない区別を含む (下記参照)。
- [ ] レイテンシの **計測**: モデル推論 + バッファリング vs 現行ワークレット。**未実施** — 決め手となる量は最小実用チャンク長であり、上流に文書化されておらず計測が必要。
- [ ] 母音フィクスチャでのエネルギーベースラインとの品質 A/B。**未実施、かつ存在しないフィクスチャによりブロック** — 「母音フィクスチャは存在しない」を参照。
- [ ] ONNX Runtime Web (WASM) のローエンドノート PC でのリアルタイム実現性。**未実施** — 依存関係が必要で、それ自体がゲートされている (#222 参照)。

## Findings

### 現在出荷されているもの

`shared/audio-lipsync.js` と `tracker/audio-lipsync-worklet.js`: AudioWorklet が RMS と low/mid/high の帯域エネルギーを計算し、**20 ms** ごと (`TARGET_POST_INTERVAL_MS`) に viseme フレームを送出、attack 30 ms / release 120 ms で平滑化し、トラッカーがそれを既存の ARKit 口チャンネルに融合する。`AUDIO_LIPSYNC_TARGET_LATENCY_MS = 80` であり、これより古いフレームは遅延再生せず破棄される。この 80 ms が置き換え候補が収まるべき予算である。

解消すべき不整合: #268 は「口と音声のオフセット 60 ms 未満、エンドツーエンド」を目標としているが、DD-003 と出荷中の定数はいずれも 80 ms である。ここではコードが正となる。issue の 60 ms は新しくより厳しいものと見られ、もし意図的であれば候補にとって条件は緩むのではなく **厳しくなる**。

### wav2arkit_cpu — 唯一ブラウザで実用可能な候補

モデルカードから確認:

| 項目 | 値 |
|---|---|
| ライセンス | Apache-2.0 |
| 成果物 | `wav2arkit_cpu.onnx`、**1.8 MB** |
| 入力 | 16 kHz モノラル float32 波形、`[batch, samples]` |
| 出力 | `[batch, frames, 52]` ARKit ブレンドシェイプ、30 fps |
| フレーム数 | `output_frames = ceil(30 × num_samples / 16000)` |
| スループット | 「音声1秒あたり約45 ms」「リアルタイムの22倍高速」 |
| 派生元 | `facebook/wav2vec2-base-960h` + `3DAIGC/LAM_audio2exp` |

1.8 MB はベンダリング済み MediaPipe モデルと比べれば誤差の範囲であり、Apache-2.0 は再配布をクリアする。どちらも強い加点である。

**しかし記載された派生元と成果物サイズは整合しない。** `wav2vec2-base-960h` は約 9500 万パラメータ — fp32 で数百 MB、int8 量子化しても数十 MB である。1.8 MB の成果物にこれは収まらない。したがって「派生元」は蒸留または大幅に切り詰めた student を意味するはずで、ベースエンコーダそのものではない。これは重要である。「Wav2Vec2 ベース」から期待される品質は、ここで期待すべき品質ではない。系譜を品質の論拠として扱う前に、エンコーダの実体を確認すること。

### レイテンシのゲート: スループットはレイテンシではない

これが issue を決する発見であり、#268 の評価計画は (「モデル推論 + バッファリング」と) 示唆しつつ最後まで追っていない。

「リアルタイムの22倍高速」「音声1秒あたり約45 ms」は **スループット** の数値である。モデルが計算律速ではないことを示し、WASM 実行プロバイダにとってこれは実際に朗報である。しかし **アルゴリズム的レイテンシ** — 現在のフレームを出力する前にどれだけの音声をバッファしなければならないか — については何も述べていない。

DD-003 の 80 ms 予算に対する計算:

- 出力は 30 fps なので、1出力フレームは **33 ms** のホップである。予算全体はおよそ2出力フレーム分の幅しかなく、既存のワークレットは自身の送出間隔で既に 20 ms を消費している。
- 文書化されている1秒のウィンドウ例を与えると **約1000 ms** のバッファ遅延が加わる — 予算の12倍超。この形ではライブ用途に使えない。
- 80 ms に収めるには、およそ 64〜80 ms (16 kHz で 1024〜1280 サンプル) のチャンクでモデルが有効である必要がある。transformer 系エンコーダがそれだけの文脈で妥当なブレンドシェイプを出力するかは **文書化されておらず**、短文脈での劣化はこの種のモデルがまさに失敗する箇所である。

つまり問題は計算量ではなくバッファリングである。採用を決める単一の計測は **出力品質が保たれる最短チャンク長と、それが 80 ms に収まるか** である。このモデルに関するそれ以外の要素はすべて有利である。

### 52出力は52チャンネルを駆動することを意味しない

issue の枠組み — 「Minamo が既に搬送している 52 個の ARKit ブレンドシェイプをそのまま出力するため、ドロップイン的な品質向上が見込める」— は適合度を過大評価している。DD-003 は意図的に音声を口チャンネル (`jawOpen`, `mouthFunnel`, `mouthPucker`, `mouthStretch*`) に限定し、視覚の信頼度が高いときは形状の所有権を視覚側に与えている。音声モデルに眉・目・視線チャンネルを書かせれば、それらをカメラから所有しているトラッカーと直接衝突する。

したがって学習済みモデルは、変更されない融合ルールの背後で、より優れた *口* 推定器として採用され、52 出力の大部分は設計上破棄される。それ自体は問題ないが、アップグレードは「ドロップイン」より狭いということであり、プロトコルが変わらないのは DD-003 の融合ルールの性質であってモデルの性質ではない。

### LAM_Audio2Expression — wav2arkit とほぼ重複

Apache-2.0、重みは HuggingFace / Aliyun OSS / ModelScope (`lam_audio2exp_streaming.tar`、サイズ非開示)、windowed と streaming の両推論スクリプト、およびブラウザ志向の WebGL アバター SDK を提供。

ORT Web 候補として個別に評価しない理由は2つ:

1. **ONNX エクスポートが公開されていない。** このリポジトリにとっては統合ではなく変換プロジェクトになる。
2. wav2arkit_cpu が既にその decoder (`3DAIGC/LAM_audio2exp`) を音声エンコーダと融合して ONNX 化したものである。LAM を独立に評価しても、より多くの手間で同じ答えを再導出することになる。

wav2arkit の短チャンク挙動がモデル特性ではなく融合/エクスポートの副作用と判明した場合に参照する上流としてのみ、引き続き関連する。

### Audio2Face-3D — ブラウザでは対象外

#268 は既にこれをブラウザ内の選択肢ではなくデスクトップコンパニオン (Tauri サイドカー) と分類しており、それは正しい判断である: 約 100 MB の PyTorch/TensorRT モデルは ORT Web の対象ではない。

正直に記録する: **issue からリンクされている NVIDIA のブログ記事には、ライセンス名、モデル出力形式、ブレンドシェイプ数、成果物サイズ、フレームワークのいずれも記載がない。** issue 本文のこれらの属性はその情報源に対して未検証であり、確認にはモデルカードまたは arXiv 2508.16401 が必要である。

情報源の問題とは別に製品上の問題もある: デスクトップ専用サイドカーとして出荷すると、同じリポジトリから出る Tauri ビルドが web ビルドより明確に優れたリップシンクを持つことになる。これは偶然発見するのではなく意図的に決めるべき乖離である。

### 母音フィクスチャは存在しない

評価計画の「母音フィクスチャ (A-I-U-E-O の分離、破裂音の閉鎖) での品質 A/B」には実行対象がない。存在するのは:

- `shared/runtime.js` の `inferVowel`。mouthOpen / mouthWide / pucker から母音を導出する **視覚** ヒューリスティックで、`src/adapters/vrm_mapper.ts` が消費する。
- `estimateAudioLipsyncFrame({ rms, low, mid, high })` を合成帯域エネルギーで呼ぶリップシンクテスト — 音声ではない。

音声フィクスチャは存在せず、リポジトリのプライバシー不変条件は録音による作成に否定的である: 生音声はコミットされない (データセットスキーマの `containsRawAudio: false`、ドラムフィクスチャは明示的にメディアではなくタイムスタンプをコミットしている)。したがって A/B ステップには **合成または TTS 生成** の母音・破裂音フィクスチャが必要であり、プライバシー規則と両立する場合のみ音声としてコミットし、そうでなければ導出特徴としてコミットする。これは今日実行できるステップではなく前提タスクである。

## Decision

**wav2arkit_cpu: 条件付きで採用。** Apache-2.0 であり、ONNX として公開され、出荷可能なほど小さく (1.8 MB)、このプロジェクトが搬送する ARKit 基底を既に出力している唯一の候補である。採用は単一の計測にゲートされる — 出力が実用に耐える最短音声チャンク長と、それが DD-003 の 80 ms 予算に収まるか。0.25 秒以上の文脈を要するならライブ経路では不採用とする。バッファリングが無償である録画の後処理など非リアルタイム用途では引き続き有用かもしれない。

**LAM_Audio2Expression: 上記に包含。** ONNX エクスポートがなく、wav2arkit がその decoder を既にエクスポートしたものである。wav2arkit の短チャンク挙動がエクスポート由来に見える場合を除き、個別評価に工数を割かない。

**Audio2Face-3D: 現時点では不採用。** 重量級でブラウザ対象ではなく、その属性は issue が引く情報源に対して未確認であり、デスクトップ専用で採用すればこのリポジトリが出荷する2つのビルド間でリップシンク品質が分裂する。

いずれにせよ **エネルギー/ヒューリスティック経路をデフォルトのまま維持する。** DD-003 の「(1) を先に出荷し、(2) は同じインターフェースの背後に」は依然有効であり、レイテンシゲートが計測される前にデフォルトを動かす根拠はここにはない。

明記すべき依存関係が2つ: これらはいずれも `onnxruntime-web` を必要とし、その追加は [onnx-wholebody-pose.md](onnx-wholebody-pose.md) (#269) と [../DEPENDENCY_POLICY.md](../DEPENDENCY_POLICY.md) が述べるサプライチェーンレビューにゲートされる — #222 が当たるのと同じゲートである。そしてこの評価の品質側は母音フィクスチャが存在するまで着手できない。
