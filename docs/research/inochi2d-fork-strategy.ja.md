# 調査: Inochi2D 分岐後の 2D パペット戦略

ステータス: issue #275 の調査パス。Inochi2D エコシステムが分岐した現在の 2D フォーマット方針を決める。関連: #38, #230,
[../design/DD-004-inochi2d.md](../design/DD-004-inochi2d.md),
[../DEPENDENCY_POLICY.md](../DEPENDENCY_POLICY.md)。

## Goal

停滞している可能性のある系統にこれ以上の統合作業を載せる前に、Minamo が nijilive フォーマットを追随すべきか、Inochi2D 0.8.x に凍結すべきか、検出により両対応すべきかを判断する。

## Acceptance criteria

- [x] Goal が明確である。
- [x] Acceptance criteria が明確である。
- [x] 既存設計と矛盾しない: 2D 経路はクリティカルパス外に留まり、ベンダリング成果物はハッシュ固定のまま。
- [x] 分岐状況、ライセンス、production 対応状況を一次情報で確認した。
- [x] 判断を記録し、再検討トリガーを定めた。
- [x] DD-004 を更新した。
- [ ] nijigenerate でエクスポートしたパペットを既存ランタイムで検証し互換性を記録する。**未実施** — nijigenerate で作成された `.inp`/`.inx` ファイルが必要であり、本パスに正当な入手手段がない。「ブロックされているもの」参照。

## Findings

### どちらの系統も、自らの表明により production 対応ではない

| プロジェクト | ライセンス | 状態 (2026-07-30 確認) |
|---|---|---|
| `Inochi2D/inox2d` (Rust、当リポジトリがベンダリング) | BSD-2-Clause | README: 「このライブラリと仕様はプロトタイプ状態であり、production での使用は推奨されない」。活発に開発中 (533 コミット) だが昇格はしていない。 |
| `nijigenerate` (エディタ、活発な fork) | BSD-2-Clause | 2026-07-26 更新 — 明らかに活動中。ただし **公式の安定ビルドなし**: nightly バイナリと weekly Flatpak のみで、「安定性は保証されない。予期せずクラッシュする可能性がある」。 |
| `nijilive` (ランタイム + 改称されたパペット標準) | BSD-2-Clause | Inochi2D v0.8 由来の nijilive Puppet 標準のリファレンス実装。 |
| オリジナル Inochi2D | BSD-2-Clause | #275 によれば最終リリース 0.8.7 (2024年9月)、v0.9/1.0 の書き直しは未出荷、自身の FAQ が依然 production 非対応と記載。 |

ライセンスの問題は明快に解決する: **nijilive と nijigenerate は BSD-2-Clause で、Inochi2D および inox2d と同一である。** fork は新たなライセンスゲートを持ち込まない。これは単独で判断を強制しえた唯一の要素だった。

したがって有用な枠組みは「どちらの系統が優れているか」ではなく「追随すべき安定した系統がまだ存在しない」である。活発な fork は自プロジェクトがクラッシュしうると述べる nightly を出荷し、当方がベンダリングする系統は自らをプロトタイプと呼ぶ。実質的に両者とも pre-1.0 である。

### 2D 経路は既にクリティカルパス外である — フラグではなくデータによって

#275 の4番目の項目は「いずれかの系統が安定するまで 2D レンダリングをクリティカルパス外 (フィーチャーフラグ) に保つ」ことを求めている。それは既に成立しており、issue が想定していなかった仕組みによる:

`viewer/viewer.js` はアセット種別でルーティングする — `['inp', 'inx', 'vrm', 'glb']` のうち `inp`/`inx` のみが `loadInochi2DFile` に到達する。したがって 2D ランタイムはユーザーが 2D パペットを与えたときにのみ起動し、それ以外では 3D 経路は無変更である。これはフィーチャーフラグより強い。誤った状態に置き残せるフラグが存在せず、2D バックエンドが VRM セッションに影響する経路もないからである。

viewer が既に `.inp` と `.inx` の **両方** の拡張子を受け付けている点も記録しておく。nijilive 期のファイルを受け取ること自体はファイル種別層でブロックされない。ベンダリングされたパーサがその *内容* を理解するかが未検証の問題である。

### ベンダリング成果物は既に正しい姿勢にある

`third_party/inochi2d-wasm/Cargo.toml` は inox2d の両クレートを単一の git リビジョン (`df8413e6…`) に固定し、`DEPENDENCY_POLICY.md` は生成された `.wasm` とその JS シムの SHA-256 も固定し、両方を併せて再ビルド・再レビューすることを要求している。

pre-production な上流に対してはこれが正しい姿勢である: **凍結と再現性、追随ではない。** 自らのビルドをクラッシュしうると述べる上流を追うことは、ハッシュ固定された成果物を移動標的に変えることであり、既存のポリシーは更新ごとにそれと衝突する。

### nicxlive が注目すべき監視対象

nijilive の C++ 実装 `nicxlive` が開発中で、OpenGL・Vulkan・DirectX・Unity および **WebGL** を対象にしていると報告されている。成熟すれば C++→WASM ビルドは Rust のプロトタイプより優れたブラウザランタイムになりうる。WebGL 対応が当方ではなく上流の関心事になるからである。計画に織り込むには早すぎる — が、現行方式の主要コストであるブラウザ対応の自前維持が解消されうる最初の兆候である。

## Decision

**固定された inox2d リビジョンに凍結したままとする。** nijilive の追随はまだ行わず、検出による両フォーマット対応も行わない。

理由:

1. 追随すべき安定系統が存在しない。活発な fork は安定リリースを持たず nightly がクラッシュしうると述べ、ベンダリング中の系統は自らをプロトタイプと呼ぶ。ある pre-production 依存から別の pre-production 依存へ移ることは何も生まない。
2. ライセンスは不変 (全て BSD-2-Clause) であり、移行を強制するものはない。
3. 「検出により両対応」は安全な保険ではなく最悪の選択肢である: 本パスが *どちらも* 実パペットで検証できない状況で、フォーマット面とベンダリング成果物を倍にする。2つの分岐の一方の実ファイルを一度も見ていない検出ロジックは負債である。
4. 現行の姿勢 — ハッシュ固定成果物、2D は 2D ファイルを与えたときのみ到達 — が既にリスクを封じている。上流の停滞は、パーサが読めないパペットを誰かが持ち込むまで何のコストも生まず、その場合も実験的経路のロード時エラーであって 3D パイプラインの退行ではない。

**以下いずれかが成立したら再検討する:**

> (1) `nijilive` がタグ付き安定リリースを公開し、**かつ** nijigenerate でエクスポートしたパペットが固定ランタイムで失敗する — すなわち移行先と移行理由の両方が揃う。または (2) `nicxlive` が WebGL/WASM ターゲットを出荷し、ブラウザランタイムを自前維持する必要が消える。

それまでは受信した `.inp`/`.inx` の失敗を戦略シグナルではなく診断データとして扱う: `viewer/inochi2d-runtime.js` は既に corrupt / BC7 / WebGL2 のロード失敗を分類しているので、nijilive フォーマットの不一致は空白キャンバスではなく識別可能なエラーとして表面化すべきである。

## ブロックされているもの

互換性テスト — #275 の最初の項目 — には現行 nijigenerate からエクスポートされた `.inp`/`.inx` ファイルが必要である。本パスに正当な入手手段はない: パペットは著作物であり、リポジトリは再配布可能なパペットをコミットしていない (これが #230 が「再配布可能な実パペットの視覚/レイテンシマトリクス」を別途追跡している理由である)。またプライバシーおよびアセットライセンスのチェックリストは任意のコミュニティファイルの取得を排除する。

このテストは「固定パーサが nijilive 期のファイルを読めるか」に答える唯一の手段であり、上記再検討トリガーの前半を左右する。nijigenerate をインストールし自身が権利を持つパペットを用意できる人が必要である。
