# 2カメラ・ドラム融合プロトタイプ

ステータス: **issue #241 のプロトタイプ結果 — ソフトウェアゲートは PASS、ハードウェアゲートは
BLOCKED。** 前提となる調査判断:
[../research/multi-camera-fusion.md](../research/multi-camera-fusion.md) (#183)。

## これで確定すること、しないこと

#183 はマルチカメラ融合を MVP 外とし、「ドキュメントのみの N/A」が動作する機能と誤認されないよう
プロトタイプゲートを #241 に委ねた。本件がそのプロトタイプである: `src/core/multiCamera.ts` と
決定論的な合成ベンチマーク。

実行対象はシミュレートされたキットであり、この区別が重要である:

- **ここで確定すること。** キャリブレーション・三角測量・クロックの数学が正しいか。棄却経路が実際に
  発火するか。第2視点が原理的に隠れた打撃を回復するか。既存の `DrumHitEvent` 経路が融合出力を
  無改造で消費できるか。カメラ2を外しても カメラ1 が動作し続けるか。
- **ここでは確定せず、#241 が開いたままである理由。** 実映像での検出精度、ローリングシャッター
  スキュー、セッションを通じたキャリブレーション安定性、そして実際のドラマーにとって設置コストに
  見合うか。これらは issue がなおブロックされている、同意済みの2カメラクリップを要する。合成
  カメラはスティック先端を完璧に見るか全く見ないかのどちらかだが、実カメラは「うまく見えない」
  のであり、機能の可否を決めるのはその場合である。

本書は #183 を実装済み機能としてクローズするものではない。

## 再現方法

```
pnpm bench:multicam          # 表
pnpm bench:multicam --json   # 機械可読
```

`scripts/bench-multicam-fusion.ts` は決定論的である — ノイズはシード付き PRNG、タイムベースは
60 fps 固定 — ため、以下の数値は1回の実行のサンプルではなく再現可能である。自己チェックを行い、
ゲートが後退した場合は非ゼロ終了する。

シナリオ: 100 bpm で4小節、9.6 秒間に 40 打。2小節はハイハット8分、2小節はライド8分、バックビート
にスネア、キャリブレート済みゾーンは3つ。`front` カメラが既定の単一ウェブカメラ、`side` が追加視点で
独自クロックを持つ。`front` は第2小節でハイハットを、第4小節でライドを見失う — 40 打中 16 打 — これが
第2アングルの存在意義たるオクルージョンである。

## 2つの層と、深度ルールが異なる理由

#183 は形を確定していた: カメラは候補を発行する独立トラッカーであり、融合段が共有フレームで整列する。
これは2層構造であり、両者の違いが読む価値のある唯一の設計判断である:

- **軌跡層** (`fuseCameraObservations`) はフレーム毎のスティック先端を **2視点** から三角測量する。
  単一視点は推測せず棄却する。1本のレイでは深度が自由に残り、それを捏造すれば `DrumHitDetector` に
  どのカメラも測っていない鉛直速度を渡すことになる — その速度こそが打撃か否かを決める。
- **候補層** (`fuseCameraHitCandidates`) は各カメラ自身の検出器が発行した打撃を統合する。ここでは
  単一視点で **十分** である。打撃とは先端がドラムヘッド上にあることを意味し、キャリブレート済みの
  ヘッド平面が欠けた深度を与えるからである。この拘束は、それを使うまさにその瞬間においてのみ有効である。

この非対称性こそがオクルージョン対応が成立する理由である。全箇所で2視点を要求すれば、`front` から
隠れた打撃は何も生まず、それは第2カメラを追加して解決したかった当の失敗である。

候補は **各カメラが報告したゾーンラベルではなく、レイの一致度** で対応付けられる。ゾーンについて
意見が割れる2台も1つの打撃を記述しており、その不一致を幾何的に決着させることが第2視点の役割である。
時刻だけで対応付けると、同一拍で叩かれたハイハットとスネアを統合してしまう。両者の交差ペアは数十
センチ離れるため、レイ一致による対応付けはそれらを分離できる。

## 結果

2026-08-06 計測、60 fps、シード付きノイズ、9.6 秒間に 40 打。

### 外部パラメータのキャリブレーション

| カメラ | チェックポイント | 平均再投影誤差 (px) | 最大 (px) | しきい値 (px) | 受理 |
|---|---|---|---|---|---|
| front | 6 | 1.69 | 3.02 | 3 | yes |
| side | 6 | 2.55 | 4.31 | 3 | yes |

しきい値は `MULTICAM_MAX_REPROJECTION_ERROR_PX = 3`。1280x720 における3ピクセルは、作業距離
1.5 m での最小キットゾーンの角サイズを十分下回るため、受理されたキャリブレーション単独で打撃が
隣接ゾーンへ移ることはない。チェックポイントが4点未満なら即座に棄却する: 剛体変換は6自由度を持ち、
3点での検証は変換が大きく誤っていても通過しうる。

### キャプチャタイムスタンプの整列

| 指標 | 実測 | しきい値 |
|---|---|---|
| 同期イベント数 | 5 | >= 3 |
| 開始時スキュー | 137.71 ms | 補正対象、ゲートしない |
| ドリフト | -2.96 ms/min | 5 ms/min |
| フィット残差 | 2.38 ms | 8 ms |
| 整列後の残存スキュー（全区間） | 0.497 ms | 8 ms |

共有された物理イベントのキャプチャ時刻ペアに最小二乗直線を当てはめる。定数スキューは補正されるため
報告のみでゲートしない。ゲートするのは **残差** — 補正後に残り、打撃タイミング誤差に直結する量 — と
**ドリフト** である。フィットは測定した区間でしか有効でないためである。5 ms/min の上限では3分間の
実行で 15 ms の外挿誤差が蓄積するが、ドラムベンチマークの 35 ms 照合許容内に収まる。

137.71 ms のスキュー自体も注目に値する: フレーム4枚分である。整列されていない2台はすべての第2カメラ
打撃を許容外に押し出すため、整列されていない第2クロックは「十分近いはず」と仮定せず棄却する。

### A/B: 同一打撃に対する1カメラと2カメラ

| 指標 | 1カメラ (front) | 2カメラ |
|---|---|---|
| 検出数 | 24 | 40 |
| 40打中の一致 | 24 | 40 |
| 適合率 | 1.000 | 1.000 |
| 再現率 | 0.600 | 1.000 |
| 誤二重打撃 | 0 | 0 |
| 平均タイミング誤差 (ms) | 1.96 | 2.21 |
| p95 タイミング誤差 (ms) | 4.37 | 5.14 |
| ゾーン精度 | 1.000 | 1.000 |
| 手割当精度 | 1.000 | 1.000 |
| 平均位置誤差 (m) | 0.0093 | 0.0070 |
| p95 位置誤差 (m) | 0.0242 | 0.0183 |
| 相互裏付けされた打撃 | 0 | 24 |

`front` が一度も見なかった 16 打はすべて第2カメラによって回復された。

これは狭く読むべきである。再現率の差はシナリオが作り込んだオクルージョンそのものなので、第2視点が
死角を **カバーしうる** ことを示すのであって、実際の front カメラがどれほど死角を持つかは示さない。
2カメラのタイミングはごくわずかに **悪い**（平均 2.21 ms 対 1.96 ms）。相互裏付けされた打撃は2台の
検出器ジッタを平均し、第2カメラのほうがノイジーだからである — 入力が非対等なとき平均化は無料では
ない。この規模では実害はないが、直感とは逆向きである。

ゾーン精度は **両方とも** 1.000 である。この配置では3ゾーンが front 視点で十分離れて投影されるため、
平面的な最近傍ゾーン判定がすでに正しく、第2カメラに直すものがない。これは実際の結果であり、明言して
おく価値がある: **この素材における第2カメラの実測上の利点はオクルージョン回復であり、ゾーン精度では
ない。** ゾーン曖昧性解消自体は検証されている — 2台が食い違う打撃を単体テストで駆動し、三角測量が
決着させる — が、ベンチマーク上では利得として現れていない。それを示すには front 視点でゾーンが重なる
キットが必要である。

### 既存検出器を通した軌跡層

三角測量された stage サンプル 872、深度を推測せず棄却した単一視点フレーム 280。真値に対する stage
位置誤差は **平均 5.7 mm、p95 10.5 mm**。これが融合に帰属する数値であり、ハーネスが強制するゲートである。

この軌跡を出荷済みの `DrumHitDetector` に流すと、40 打に対し 81 検出、再現率 0.625、タイミング
バイアス中央値 −81.4 ms となる。

### 発見: DrumHitDetector は下降中に再発火する

上記の過剰計数は融合の誤りではない — 入力軌跡はミリメートル精度である。これは `DrumHitDetector` の
性質であり、本プロトタイプが初めて表面化させたものである。リポジトリが計量的な stage フレーム軌跡を
持ったのが初めてだからである:

ゾーンはヘッド中心まわりの **球** であり、検出器は先端が球内にあり `DRUM_DOWNSTROKE_MIN_SPEED_MPS`
より速く下降し、再アームされたか `cooldownMs` を過ぎていれば発火する。現実的なキットでは半径が
**打撃間にスティックを持ち上げる高さを超える** — 14インチのスネアは半径 0.18 m、スティックの
持ち上げは約 0.11 m — ため、先端が球から出ない。#123 のリバウンド再アームは直前の発火時の y に対して
持ち上げを測るが、その y は *頂点* 付近なので再アームもされない。結果として `cooldownMs` だけが制限と
なり、下降の全区間でクールダウン毎に打撃が連発し、ヘッドの数センチ上で発火する。実測の −81.4 ms
バイアスはその最初の早期発火である。

#123 のリバウンドテストがこれを捉えないのは、打撃フェーズごとに1サンプルしか与えないためである。この
現象は連続サンプリングされた下降がなければ現れない。

**ここでは修正しない。** 打撃の発火タイミングを変えるのは #121/#235 に属するドラム検出の作業であり、
実クリップに対する調整を要する — 有力な修正案（鉛直速度の符号反転で発火する、再アームを発火時の y では
なく観測された最低 y から測る）はいずれも #123 が守ろうとした高速ロール挙動とトレードオフになる。
実ドラム検証を行う者が驚かないよう、また上記の打撃数を融合の結果と読まれないよう記録する。

### カメラ2の切断

第2カメラを登録から外し他は一切変えない場合、`front` は使用可能なまま、`degradedToSingleCamera` は
true、24 打が引き続き生成され、1カメラ・ベースラインと完全に一致する。第2カメラは加算的であり、
第1カメラを道連れにはできない。

## 融合される前にソースが証明すべきこと

#183 の警告が「数学を間違えること」ではなく「非互換な座標を混ぜること」に向けられていたため、すべての
棄却は機械的で、理由付きで報告される:

| 理由 | 発火条件 |
|---|---|
| `uncalibrated` | 再投影チェックを通過していない |
| `stageFrameMismatch` | 2台が異なる stage フレームを名乗る — 多数決ではなく **全台** を失格させる |
| `clockUnaligned` | 基準以外のカメラが受理済みクロックモデルを持たない |
| `stale` | 観測が `MULTICAM_MAX_SAMPLE_AGE_MS` より古い |
| `nonFinite` | 時刻・画像点・信頼度に NaN/Infinity がある |
| `lowConfidence` | `MULTICAM_MIN_OBSERVATION_CONFIDENCE` 未満 |
| `behindCamera` | 画像点が有効なレイに逆投影されない |
| `singleView` | 軌跡層のみ: 1視点のため深度が不明 |
| `parallelRays` | 2本のレイが平行に近すぎて三角測量できない |
| `rayGap` | 2視点の空間的食い違いが `MULTICAM_MAX_RAY_GAP_M` を超える |
| `duplicate` | 1台が統合窓内に同一ゾーンを2度報告した |
| `noZoneIntersection` | 解決点がどのキャリブレート済みヘッド上にもない |

`rayGap` 経路がマルチカメラ偽陽性のガードであり、覚えておく価値がある: これがなければ、キャリブレー
ションがずれた第2カメラはすべての打撃を二重発火に変え、第2カメラがないほうが厳密にましになる。

## 副次的発見: ベンチマーク採点器はバックビートを測れなかった

A/B の構築過程で `scoreDrumBenchmarkEvents` の欠陥が判明し、同一変更で修正した。期待打撃と検出を
**時刻のみ** で対応付けていた。ほとんどのグルーヴでは2つの手足が同一拍に着地する — ハイハット8分の
下のバックビートスネアが典型例 — ため、スネアの期待打撃がハイハットの検出を消費しうる。ゾーンが完全に
正しい実行が、バックビート毎に1件のゾーン誤りとして採点され、奪われた検出は正解を待っていた側の
再現率も押し下げていた。

現在は2パス方式である: 同一ゾーンのペアを先に確保し、残りを従来どおりゾーン横断で対応付ける。真の
誤帰属は引き続き誤りとして計上され、`zoneId` を持たない期待打撃は従来の挙動を維持する。これは1拍に
2つの手足が乗る記録済みドラムベンチマークすべてに影響するため、そうしたクリップの既存のゾーン精度・
手割当精度は悲観的だったことになる。

## #241 に残るゲート

ソフトウェア（本件で完了）: 測定されたしきい値付きの外部キャリブレーション、タイムスタンプのスキューと
ドリフト、既存 `DrumHitEvent` 経路を通した候補融合、stale/未キャリブレーション/フレーム非互換ソースの
明示的棄却、1カメラ対2カメラの A/B。

ハードウェア（未了）: 1つのキットに実カメラ2台、同意済みクリップ、実キャプチャから測った再投影誤差と
クロックドリフト、その素材での A/B 再実行、および PR #220 のテンプレートを用いた環境・同意・コミットの
エビデンス記録。生映像は終始各キャプチャ端末に留まる。本プロトタイプはフレームを端末外に一切移動しない。
