# トラッキングフレーム E2EE

ステータス: `shared/e2ee.js` に実装されたリファレンスプロファイル。

Minamo リレーはトラッキングフレームを読む必要はありません。E2EE プロファイルは、各 KGM フレームが WebSocket または WebTransport に入る前に封印します。リレーは不透明なバイトのみを見て、KGM1/KGM2 をデコードすることなくフレームを転送し続けます。要するに、リレーは不透明なバイトのみを見ます。

## フレームフォーマット

```text
nonce u8x12 | AES-GCM ciphertext+tag
```

エンベロープバージョン 2 は、完全にランダムな 96 ビットの AES-GCM ノンスをフレームごとに送信します。ルーム全体で共通する決定的なプレフィックスがないため、独立した送信者が従来の 64 ビット乱数空間を共有することはありません。AES-GCM の認証タグは 96 ビットで、フレームごとのオーバーヘッドは引き続き正確に 24 バイトです。

プロファイル識別子 `minamo.kgm.e2ee.v2` は追加認証データとして認証されます。そのため、バージョン 1 のパケットをモーションデータとして誤解釈せず、認証エラーとして拒否します。

## キー導出

`deriveRoomKey(secret, room)` は WebCrypto PBKDF2-SHA-256 を使用し、抽出不可能な HKDF ベースキーを導出します。完全なランダムノンスごとに HKDF-SHA-256 で新しい抽出不可能な AES-256-GCM フレームキーを導出します。このフレーム単位のリキーにより、各 AES-GCM キーの使用は 1 メッセージに限定されます。ルームシークレットは、リレーに送信されない URL フラグメントなどの手段で共有します。

## 失敗時の動作

`decryptFrame()` は次のエラーをスローします:

```text
Unable to decrypt tracking frame: wrong room key or corrupted frame
```

ビューワーは、ゴミの動きをデコードしようとするのではなく、そのメッセージを表示しなければなりません。テストは、間違ったキーがこの明確なエラーで拒否されることを確認します。

## 検証

`pnpm test` は以下をカバーします:

- ciphertext はプレーンテキスト KGM1 フレームを含まない
- 正しいキーで復号化すると元のフレームバイトが返される
- 間違ったキーでの復号化は明確なエラーで失敗する
- 独立した送信者が完全な 96 ビットのランダムノンス欄を使用する
- バージョン 2 プロファイルが従来のバージョン 1 エンベロープを拒否する
- オーバーヘッドはフレームごとに正確に 24 バイトである

## ノート

このプロファイルは、暗号化バンドルを追加せずブラウザで利用できる WebCrypto HKDF と AES-GCM を使用します。KGM-037 の受け入れ基準は、リレーの不透明性、オーバーヘッド、および間違ったキーの動作に関するものです。将来 Minamo が XChaCha20-Poly1305 用に libsodium を導入する場合や IETF MoQ Secure Objects にエンベロープを整合させる場合も、同じ `shared/e2ee.js` インターフェースを維持するべきです。

バージョン 2 では MoQ Secure Objects を直接採用しません。Minamo は WebSocket と WebTransport の両方で同じコンパクトなエンベロープを必要とし、当該ドラフトもまだ発展中だからです。トランスポート層での評価は Issue #274 で追跡します。将来のワイヤーフォーマットを標準化する前に、送信者別キーとノンスに関する指針を再評価します。
